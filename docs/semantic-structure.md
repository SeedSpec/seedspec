# Why structure exists

> Informative. Adds no requirements beyond the protocol.

A capable model can build from a prompt. A well-written Markdown file can
be an excellent implementation input. Adding files or YAML does not
automatically improve either one.

Structure earns its keep when meaning must survive a handoff: author to
adopter, team to team, catalog to project, one agent to another. An
informal document can contain everything and still leave every recipient
to reconstruct what is authoritative, what is an example, and what would
count as success.

## Roles 0.4 actually has

| Role | Question |
| --- | --- |
| Prose in `SPEC.md` | What is the destination? |
| Configuration | What may this adopter choose, and what does the choice change? |
| Success criteria | What claims would show the destination was reached? |
| Capabilities | What observable behavior does this package name? |
| Tasks | What ordered reminders did the author want an agent to see? |
| Context modules | What supporting material travels with the package? |
| Bundled children | Which exact other packages are part of this one? |

Adopter selections, authoring notes, and verification results are not
package roles. They are project or product state.

## What structure is for

- Keep example values from becoming silent selections.
- Keep implementation advice from becoming product intent.
- Keep a digest so “these bytes” is a fact.
- Keep optional children and profiles from mutating the authored package.

It is not for making the agent deterministic, filling folders for
appearance, or proving that a realization exists.

## Authoring is a separate claim

Protocol validity means the package can be interpreted. It does not mean
the author found the important rules. Guided authoring can help. It does
not become a conformance requirement, and its workspace is not package
content.
